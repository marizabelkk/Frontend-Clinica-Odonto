Definir o contrato de comunicação entre o frontend Flutter e o backend Flask para o MVP de Semiologia,
incluindo padrões gerais, autenticação, autorização, endpoints, formatos de request e response, estados da ficha,
regras de negócio e erros HTTP.

Acesso: Autenticado. Retorna os dados do usuário correspondente ao token.

7. Convenções HTTP e JSON
POST será usado para criação de recursos ou decisões registradas como novos eventos. PATCH será usado para
alteração parcial ou transição de estado de um recurso existente. GET será usado para consulta.
O cliente não deve enviar IDs de usuário para substituir a identidade do token. O backend identifica aluno e
professor pelo JWT.
8. Usuários
8.1 Criar usuário
POST /usuarios
Acesso: ADMIN.
A interface administrativa de cadastro de usuários não integra o MVP, mas a rota poderá existir estruturalmente.
9. Pacientes
9.1 Buscar pacientes
GET /pacientes
Acesso: Autenticado.
Filtros previstos:
 GET /pacientes?busca=Maria GET /pacientes?cpf=12345678901
9.2 Cadastrar paciente
POST /pacientes
Acesso: ALUNO, ADMIN.
Ao cadastrar um paciente, o backend deverá criar automaticamente o prontuário 1:1 associado.
Request:
 { "nome_completo": "Maria Oliveira", "cpf": "12345678901", "rg": "MG123456", "data_nascimento":
"1995-04-12", "sexo": "Feminino", "celular": "31999998888" }
Response:
 { "paciente_id": 10, "prontuario_id": 8, "nome_completo": "Maria Oliveira" }

14. Ficha de Semiologia
14.1 Criar ficha
POST /atendimentos/{id}/fichas/semiologia
Acesso: ALUNO responsável.
Cria uma ficha de Semiologia com status inicial RASCUNHO.
Response de exemplo:
 { "id": 201, "atendimento_id": 155, "status": "RASCUNHO", "versao": 1 }
14.2 Consultar ficha
GET /fichas/{id}
Acesso: usuário autorizado.
14.3 Salvar rascunho ou correção
PATCH /fichas/{id}
Acesso: ALUNO responsável.
Permitido quando a ficha estiver em RASCUNHO ou CORRECAO_SOLICITADA.
Request parcial de exemplo:
 { "queixa_principal": "Dor na região inferior esquerda", "historia_doenca_atual": "Paciente
relata dor há cinco dias." }
15. Submissão da ficha
PATCH /fichas/{id}/submeter
Acesso: ALUNO responsável.
A mesma ação será utilizada tanto no primeiro envio quanto no reenvio após correção.
Transições permitidas:

RASCUNHO -> AGUARDANDO_APROVACAO

CORRECAO_SOLICITADA -> AGUARDANDO_APROVACAO
Response:
 { "id": 201, "status": "AGUARDANDO_APROVACAO" }

16.2 Registrar decisão
POST /fichas/{id}/aprovacoes
Acesso: PROFESSOR.
Solicitar correção:

}
Aprovar:
 { "decisao": "APROVADA", "observacao": null }
Cada decisão deverá gerar um novo registro de aprovação/revisão e atualizar o status da ficha.
17. Odontograma
17.1 Consultar odontograma
GET /prontuarios/{prontuario_id}/odontograma
Acesso: Autenticado.
17.2 Registrar condição odontológica
POST /atendimentos/{atendimento_id}/odontograma/registros
Acesso: ALUNO responsável.
Request:
 { "numero_dente": 36, "face": "OCLUSAL", "condicao_id": 4, "observacao": null }
O backend utiliza o atendimento para determinar o contexto do prontuário e do odontograma.
18. Exames complementares - módulo previsto
A Semiologia v2 prevê exames complementares, porém o contrato definitivo desse módulo depende da modelagem
detalhada.
Rotas conceitualmente previstas, ainda não consolidadas:
 POST /atendimentos/{id}/exames GET /pacientes/{id}/exames
Anexos e upload de arquivos não serão fechados nesta versão.
19. Consentimento e assinatura - módulo previsto
O sistema deverá suportar consentimento e assinatura associados ao paciente e atendimento/ficha.
Os endpoints definitivos dependem da validação do termo institucional e da decisão sobre armazenamento da
assinatura.
Nenhuma estratégia de Base64, arquivo ou object storage é considerada oficial neste contrato.

21. Regras de negócio

Somente o aluno responsável edita a ficha em RASCUNHO ou CORRECAO_SOLICITADA.

AGUARDANDO_APROVACAO não permanece livremente editável pelo aluno.

Somente professor autorizado registra decisão de correção ou aprovação.

APROVADA é considerada finalizada; mudanças posteriores dependem da estratégia de versionamento.

O backend identifica aluno e professor pelo JWT.

IDs enviados pelo cliente não substituem autorização.

Condições médicas, alergias e medicamentos são informações clínicas compartilhadas.

Sinais vitais pertencem ao atendimento.

O odontograma registra condição clínica por dente/face e mantém vínculo com o atendimento e usuário.

24. Governança do contrato
O presente documento é a referência manual consolidada do contrato entre frontend e backend.
Após a implementação dos endpoints, a especificação OpenAPI gerada automaticamente pelo backend será
a referência executável oficial.
Não deverá existir uma segunda lista manual de endpoints divergente da implementação.
Mudanças em rotas, métodos, campos, enums, tipos ou respostas deverão ser combinadas entre frontend e
backend antes de entrar no código e refletidas no Swagger/OpenAPI.
25. Observação final
Esta versão substitui o Contrato Inicial da API v1 e a documentação manual Swagger/OpenAPI v1.1 como
referência consolidada de integração.
O objetivo é manter uma única fonte coerente para o MVP, reduzir divergências entre documentos e permitir que
Flutter e Flask sejam desenvolvidos em paralelo.
